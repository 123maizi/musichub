# MusicHub 1.4.8

修掉底部缩略进度条的两个缺陷。这两个都不是「手感差一点」，是可复现的缺陷，根因都已定位到浏览器行为层面。

## 一、快速滑到最开头后：歌不跟着走、缩略条不动

**根因：Chromium 的原生 range 会漏发 `change`，而提交路径只挂在 `change` 上。**

事件取证（真实鼠标事件，同一构建、同样的快速甩动，连续两次逐字对比）：

| | 事件序列 |
|---|---|
| 成功那次 | pointerdown → mousedown → input×3 → pointerup → mouseup → **change** → click → lostpointercapture |
| 失败那次 | pointerdown → mousedown → input×3 → pointerup → mouseup → click → lostpointercapture |

`input` 一路都在（值确实拖到了最开头），**只有 change 没来**，时好时坏。漏发之后：

- `seeking` 永不释放 → 显示被拖动值钉住 → **条子不动**
- `player.seek()` 没被调用 → 音频继续在原处播 → **歌不跟随缩略条**
- 2 秒看门狗只释放状态、**把这一下拖动整个丢掉** → 条子又弹回真实位置

正在播放页那条之所以看起来正常，是因为它当时没在拖动、显示的是真实进度。

**修法**：`pointerup` / `lostpointercapture` / `pointercancel` / 窗口级 `pointerup` 任一到达即提交；
再加一道「拖动静默 320ms 就当作结束」的兜底提交（松手事件丢在窗口外也照样落位）。

## 二、点击进度条跳转有偏差

**根因：原生 range 的 value 被 `step` 量化。** `step=5` → 落点最多偏 2.5 秒，
在 1320px 轨道上是 12px（实测 60% 处点一下：落到 160.0 秒，期望 161.9 秒，偏 −1.9 秒）。
`step` 不能改小 —— 实测 `step=0.1` 会让指针命中整体坏掉（误差 −12/−76.6/−141px、回弹 146 帧）。

**修法**：落点与拖动预览改由指针横坐标反算（与 Chromium 相同的映射），`step` 继续只服务键盘。
另外拖动中关掉填充/滑块的 520ms 过渡 —— 带着缓动拖，填充必然落后于指针。

## 三、顺带把两条进度条合成一份实现

底部缩略条与正在播放页的大进度条原本各写一份几乎相同的逻辑，然后各自演化。
现在共用 `src/renderer/src/composables/useSeekBar.ts`，修一处即两条一起修。

## 实测

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 点击落点误差 | 最多 −2.5 秒（step 量化） | **≤ 0.2 秒**（1320px 轨道） |
| 拖动中「填充 vs 指针」偏差 | 量化 + 520ms 缓动 | **0.00%（0px）**；大进度条 ≤1px |
| 拖动工况矩阵（7 种甩/拖/松手方式） | 7 个里 3 个被吞 | **7/7 生效** |
| 键盘 ←/→ 步进 | 正常 | 正常（±5 秒/次） |
| 全功能验收 | 11/11 | **11/11** |

拖动工况矩阵覆盖：快速甩到最左（松手在边缘）、甩到中间、中速拖、慢速拖、
松手前停顿、松手点移出控件、单步直达 —— 7 种全部提交且音频准确落位。
