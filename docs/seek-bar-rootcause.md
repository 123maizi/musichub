# 进度条两个 bug 的根因（1.4.8）

两个症状都出在底部播放条那条缩略进度条上。**都不是「差一点」的手感问题，是可复现的缺陷。**

---

## 一、快速滑到最开头后：歌不跟着走、条子不动

### 结论

`change` 事件只挂在提交路径上，而 **Chromium 的原生 range 会漏发 `change`**。

### 证据（真实鼠标，CDP Input 派发；`scripts/seek-lab.mjs trace`）

同一次运行里连续两次同样的「快速甩到最左」，事件序列逐字对比：

| | 事件序列 |
|---|---|
| 成功那次 | `pointerdown` `mousedown` `input`×3 `pointerup` `mouseup` **`change`** `click` `lostpointercapture` |
| 失败那次 | `pointerdown` `mousedown` `input`×3 `pointerup` `mouseup` `click` `lostpointercapture` |

`input` 一路都在（值确实拖到了 0），**只有 `change` 没来**。同一台机器、同一构建，时好时坏。

### 为什么会变成「条子不动 + 歌不跟随」

旧代码的三处都依赖 `change`：

1. `seeking` 不会变回 false → 显示值被 `seekValue` 钉死在拖动位置 → **条子不动**
2. `player.seek()` 没被调用 → 音频继续在旧位置播 → **歌不跟随缩略条**
3. 2 秒看门狗只把 `seeking` 放开，**把这一下拖动整个丢掉** → 条子弹回真实位置

而大进度条（正在播放页）当时没在拖动，所以它显示的是真实进度 ——
这才有「只跟随详略图中的进度条」这个现象。

### 修法

- 提交不再只认 `change`：`pointerup` / `lostpointercapture` / `pointercancel` / 窗口级 `pointerup` 任意一个到达即提交（幂等，带时间窗去重）
- 加「拖动静默 320ms 即当作结束」的兜底：松手事件丢在窗口外也照样落位
- 两条进度条合并到 `src/renderer/src/composables/useSeekBar.ts` 一份实现 ——
  各写一份正是「缩略条坏了、大条还好的」这类现象的来源

## 二、点击进度条跳转有偏差

### 结论

原生 range 的 value 被 `step` 量化。`step=5` → 落点最多偏半个步长 = 2.5 秒；
在 1320px 的轨道上是 **12px** 的可见偏差（实测 60% 处点一下，落点 160s vs 期望 161.9s，偏 −1.9s / −9px）。

`step` 不能改小：`step=0.1` 会让指针命中整体坏掉（历史实测误差 −12/−76.6/−141px、回弹 146 帧，已回退）。

### 修法

落点与预览改由 `clientX` 反算（与 Chromium 相同的「两端各内缩半个原生滑块」映射），
`step` 继续只服务键盘。另外拖动中关掉填充/滑块的 520ms 过渡 ——
带着缓动拖，填充必然落后于指针，那也是「有偏差」的观感来源。

### 实测（1320px 轨道）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 点击落点误差 | 最多 −2.5s（step 量化） | **≤0.2s** |
| 拖动中「填充 vs 指针」偏差 | step 量化 + 520ms 缓动 | **0.00%（0px）** |
| 拖动工况矩阵（7 种甩/拖方式） | 7 个里 3 个被吞 | **7/7 生效** |

## 探针自己踩过的坑（记下来免得重复）

1. **合成事件测不出指针 bug**。旧探针 `input.value = ...; dispatchEvent(new Event('change'))`
   完全绕过浏览器的「坐标 → 数值」映射。必须用 CDP `Input.dispatchMouseEvent`。
2. **拖动中的 `mouseMoved` 必须带 `button:'left'` + `buttons:1`**。
   按 CDP 文档写成 `button:'none'` 时滑块的取值**完全不动**，
   看起来就像「拖了没反应」的产品缺陷 —— 其实是工装的问题。
3. **逐帧表不能用定宽补空格拼接**。`data-progress` 是 18 位浮点字符串，
   撑破列宽会把后面所有列挤位，我因此把一次正常运行读成了
   「`--p`=0 而 display=2.34 且 seeking=true」这种自相矛盾的状态。
4. **前置缺失要自己喊停**。没先给 `window.Audio` 打桩就测，`el` 为空，
   7 个工况会全部报「音频没到落点」—— 看着像功能全废，其实是真值列是空的。
   现在 `matrix` / `clicks` 会直接以退出码 3 拒绝给结论。
5. **测哪一条进度条，先确认那一条在最上层**。1280×800 下正在播放页的进度条
   被固定的底部播放条压住，`elementFromPoint` 命中的是缩略条：
   点击「看起来」偏了 −12/−55 秒，其实是那一下点在了缩略条上、按缩略条算得好好的。
