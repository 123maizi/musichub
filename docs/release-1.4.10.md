# MusicHub 1.4.10

这一版修四件事，其中第一条是**我上一版（1.4.9）引入的回归**，先说清楚。

---

## 一、先认账：1.4.9 让不少歌丢了译文

用户报「很多本来还有一半中文歌词的歌，现在完全没有中文翻译了」。查实是我 1.4.9 引入的：

**根因**：我在 `loadTranslationOptions` 开头写了 `if (translationLoading.value) return`，
本意是「同一首歌别重复请求」，实际效果是 —— **A 歌的译文还在路上时切到 B 歌，
B 歌的请求被整段丢掉**，B 永远拿不到译文。而 1.4.9 新加的宽松匹配会把请求拉长到几秒，
窗口被显著放大，于是表现为「很多歌都没译文了」。

**修法**：
1. 互斥改成**按歌判断**（同一首歌才跳过），绝不挡住别的歌
2. 加 9 秒硬超时：主进程那条链路最多打 4 次网络请求，任何一次挂住都会让 Promise 不落地，
   旧写法下界面会永远停在「正在查找现成译文…」并且**后续所有歌一起卡住**
3. 补一道「**不许把译文换差**」的保护：自动应用现成译文时，只有覆盖行数**多于现有译文**
   才替换。旧逻辑只看「当前有没有译文」，于是一份 3 行的宽松匹配结果就能把用户那半份译文顶掉
4. 自动应用的最低门槛（≥4 行且 ≥主歌词 15%），挡住「几行巧合」

## 二、中文译文要「完整」，不能只给一半

平台给的现成译文**本身就常常没翻全**（实测真实接口）：

| 曲目 | 现成译文覆盖 / 歌词行数 |
|---|---|
| Lemon | 43 / 57 |
| LOSER | 38 / 85 |
| Yellow | 40 / 54 |
| Shape of You | 88 / 92 |

这种情况再怎么对齐也补不出来 —— 那些行平台侧就没有译文（副歌、重复段、念白）。

**修法**：
- **只把缺译文的那几行**交给翻译（不是整首重翻），分批处理（每批 18 行），
  成功一批就立刻并进去，用户能看到译文一行行补上
- **已有译文一行都不动**：模型只填空，绝不覆盖官方译文或用户手工改过的行
- **信息行不翻**：作词/作曲/制作人这类 credits 不需要中文，实测补齐一批 18 行要 9.9 秒，
  把它们排除后要补的往往只剩几行，既快又准
- 整首都没有译文的歌也自动补（同样的前提：非中文歌词、用户没主动清过）
- 补齐结果按歌缓存：重播直接套缓存，不重复花钱也不会掉回一半

**实测（同一批歌，与 1.4.9 出厂包对比）**：

| 曲目 | 1.4.9 未译行数 | 1.4.10 未译行数 |
|---|---|---|
| Shape of You | 50 | **25** |
| Blinding Lights | 17 | **9** |
| Lemon | 14 | **2** |

残留的那些不是漏翻：`制作人 : Steve Mac`、`作词 : …` 这类信息行，
以及 `·`、`Oh—i—oh—i`、`Yeah`、`Hey, hey, hey` 这类没有语义的拟声/分隔行。

## 三、先出原文歌词，别再让人干等

用户的原话：「先获取英文原版歌词再获取中文翻译歌词，不然它一直卡好久才显示歌词，
让人误以为没有歌词」。

**根因**：歌词链路原来是**串行**的 —— 音源链逐个试完，再走内置链；内置链内部还是
QQ 试完再试网易云。四段排队，任何一段慢都会累加（实测最坏 13.2 秒才出现第一行歌词）。

**修法**：音源链与内置链**同时开跑，谁先给出非空歌词就用谁**；内置链内部 QQ 与网易云也并发。
不是简单的 `Promise.race` —— 两边都可能正当地返回「这首歌没有歌词」，
只有非空才算赢，否则先到的 null 会把还在跑的好结果一起废掉。

**实测**：点播放 → 第一行歌词出现，中位数 **2143ms → 770ms**，最坏 **3209ms → 1395ms**。

## 四、删掉「设置 → 默认播放音质」

它和播放条上的音质快选**互相打脸**：在播放条上选了无损，下一首歌又被设置里的「默认值」改回去。
现在唯一来源就是播放条上的快选，并且**落盘**（`prefs.playQuality`），重启也在。

顺带修掉一个安静的 bug：偏好存储的 `get()` 里漏了新字段的读取 ——
值确实写进了 JSON 文件，但渲染层永远读回 undefined，「落盘成功却等于没存」。
音源没有该音质时仍按既有行为自动降级。

**实测**：设置页已无该项；在播放条选 Hi-Res → prefs 写入 `flac24bit`；
换到另一首歌后仍显示 `24BIT`。

## 五、解析播放速度：**没有回归**

用户强调「最主要的！！改完以上所有bug不能影响歌曲的解析播放速度」。实测：

| 指标 | 基线（1.4.9） | 1.4.10 |
|---|---|---|
| 点击到出声：最快 | 28 ms | 28 ms |
| 点击到出声：最慢 | 483 ms | 483 ms |
| 点击到出声：平均 | 175 ms | **175 ms** |
| 缓存命中后再播 | 26 ms | **26 ms** |

歌词相关的改动全在**播放链路之外**（歌词请求与取流本来就并发），
且新增的翻译补齐全在后台跑，不阻塞播放。

全功能验收 11/11 通过。

## 探针自己踩的坑（记下来免得重复）

1. **「连续两次采样相同就算稳定」是错的**。补齐在后台跑，会先安静好几秒等接口，
   那种判据第一次就判定稳定，量到的其实是补齐之前的值 —— 我因此得出过
   「新旧构建数字一模一样，补齐没生效」的错误结论。改成等固定足够长时间。
2. **歌词 DOM 只在「正在播放」页存在**，在搜索页轮询 `.lyric-line` 永远为 0，
   会把「歌词没出来」误判成功能坏了。
3. **必须同时校验「当前是哪首歌」**：换歌没生效时读到的是上一首的数据，
   我差点把 A 歌的 92 行歌词当成 B 歌的结果。
4. **注入页面的对象字面量里，键名不能含「」这类标点**（`「要不要翻」这道闸门: ...`
   直接是语法错误），中文键名只能是纯文字。
5. **IPC 层搜索结果的 `platform` 是小写 id**（`kg`），不是界面上的短名（`KG`）。
