# seekpos 探针的假数据来源（重要，别再被骗第三次）

## 症状
`playerfix-seekpos.mjs` 会间歇性报出：
```
点击误差px: -11 ~ -14 / -74 ~ -80 / -137 ~ -141
回弹帧数:   73+73=147 ~ 159
拖动最大误差: 109 ~ 113px
```
这组数字**看起来像「点击/拖动彻底坏了」**，但它出现时**产品其实没问题**。

## 根因：range 处于 disabled 状态（没有歌在播）
直接在页面上量到：
```
"step": "5"      ← 刻度是对的
"max": "0"       ← duration 为 0 → 输入框 disabled
```
`<input type="range" :disabled="!player.current || player.duration <= 0">`
没有歌时它是禁用的，**点击、拖动都不会派发 input 事件**。
于是探针点半天没反应，填充只跟着播放缓慢前进 ——
在 270px 轨道上就表现为「误差随位置线性拉大 + 大量回弹帧」的假象。

## 正反证据
| 场景 | 点击误差 | 回弹帧 |
|---|---|---|
| **有歌在播**（`max=172`） | **+1.42 / −1.31 / +3.76px** | **0** |
| 没歌（`max=0`，disabled） | −11 ~ −14 / −76 / −141px | 147 ~ 159 |

同一支探针、同一份构建，唯一差别是「有没有歌在播」。

## 影响范围（已经被这个假象骗过三次）
1. player-fix 报的「新构建出现回归」—— 其实就是这个
2. 我据此错判「是我改 step 弄坏的」，做了不必要的改动又回退
3. 期间还混入了另外两个陷阱（半新半旧的构建产物、隐藏窗口 rAF 停摆）

## 要求
**所有 seek/指针类探针在开跑前必须断言前置条件**，不满足就直接拒绝出数：
```js
const el = document.querySelector('input.seek')
if (!el || el.disabled || Number(el.max) <= 0) {
  throw new Error('前置条件不满足：没有歌曲在播（range disabled, max=' + el?.max + '）。拒绝出数。')
}
```
另需一并带上（前两次教训）：
- **环境守卫**：`document.hidden === false` 且 600ms 内 rAF 帧数 > 10
- **build id**：`out/renderer/index.html` 的 mtime + 入口 chunk 文件名
- **目标校验**：确认探针连的是自己那个端口的实例（9222 归用户，队员用 9223+）

## 当前产品状态
- 位置来源唯一化（`pendingSeek` 目标值 + 600ms 兜底）→ 有歌时回弹帧 **0**
- 原生 range 滑块收窄到 2px → 消除 Chromium「按半个滑块内缩可点区间」的固定偏差
- 键盘 +5 秒：真实按键步进 **5.2 秒** ✓（`stepUp()` 只走 1 档，探针若用它测会误判）
- 布局代价未回退：`var` 与地板值齐平（0.050 vs 0.058）
- `step=5` 保持不动：理论上最坏量化误差 ≈3.9px，但**实测有歌时误差只有 1.4~3.8px**，
  不值得为这点理论值去动 step（我试过改成 0.1，虽然那次失败其实是 disabled 假象，
  但既然现状已达标，就不要引入新变量）
